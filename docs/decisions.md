# Decisions

Append only. Each entry says what was decided, why, and what was rejected. Design-system decisions are in `design-system/docs/decisions.md`.

| ID | Date | Decision | Why | Rejected |
|---|---|---|---|---|
| F-1 | 2026-11-12 | React 19, TypeScript, Vite, client-rendered. One app per product in a pnpm monorepo with Nx as task runner. | Every app sits behind sign-in and is highly interactive; server rendering adds cost without benefit. One app per product keeps bundles and failures separate. | Next.js; one large app; runtime micro-frontends. |
| F-2 | 2026-11-12 | TypeScript pinned to 5.9. | TypeScript 7 broke the API type generator (needs the 5.x compiler API) and is outside the range the lint tooling supports. | Latest TypeScript. Revisit when `openapi-typescript` and `typescript-eslint` support it. |
| F-3 | 2026-11-12 | Package boundaries are enforced by `scripts/check-boundaries.mjs`, not by Nx's lint rule. | In testing, the Nx rule skipped itself with a warning when its project graph cache was missing. A guard that can silently not run is not a guard. The script is deterministic and was tested against planted violations. | `@nx/enforce-module-boundaries`. |
| F-4 | 2026-11-12 | Access token in memory only; refresh token in session storage. | The backend returns both tokens in the response body. Memory-only access tokens limit what script injection can steal; session storage limits the refresh token to the tab's lifetime. | Local storage (survives longer, larger theft window). **Better, needs backend work:** deliver the refresh token as an `HttpOnly`, `Secure`, `SameSite` cookie so no script can read it. Until then a successful script injection could steal a refresh token. |
| F-5 | 2026-11-12 | Response types are hand-written in `packages/api-client/src/types.ts`. | The backend's OpenAPI description declares request bodies but no response bodies. | Guessing shapes; skipping types. **Needs backend work:** add response decorators so these can be generated. |
| F-6 | 2026-11-12 | Browser tests run against a mock backend in `e2e/support/api.ts`. | Fast, deterministic, no database needed in CI. | Running the real backend in CI for every pull request. A staging smoke test against the real backend is still needed (roadmap). |
| F-7 | 2026-11-12 | Mobile Safari (WebKit) tests run in CI only by default. | The current WebKit build does not run on the development machine's macOS version. Locally: `E2E_WEBKIT=1 pnpm e2e` on a supported system. | Dropping WebKit coverage. |
| F-8 | 2026-11-12 | The design system moved into this repository: tokens and UI code as packages, written docs under `design-system/`. This copy is canonical. | Agents here need the specs and tokens beside the code they govern. | Keeping it in the backend repository. The copy there should be removed to avoid two sources of truth. |
| F-9 | 2026-11-12 | Plain CSS on tokens; no CSS-in-JS, no utility framework. | The token layer already is the abstraction, and a check proves every value is a token. | Tailwind; styled-components. |
| F-10 | 2026-11-12 | Agents merge through GitHub auto-merge behind three required checks; no agent holds merge permission. | The owner asked for unattended merging once QA, desktop and mobile tests, all other tests and security checks pass with reviewer approval. Auto-merge makes GitHub, not an agent, the one that decides the checks are green. | Agents calling merge directly; requiring a human approval on every pull request. |
| F-11 | 2026-11-12 | The accessibility scan excludes React Aria's hidden live-announcer node. | After a pending button unmounts, the announcer keeps a reference to its label, which the scanner reports. It is invisible library plumbing, not product markup. | Disabling the rule everywhere. |
| F-12 | 2026-11-12 | Translation is not set up yet; strings are collected in per-feature `messages.ts` files. | Keeps every string in one place per feature so a translation library can be added without touching components. | Adding a translation library before there is a second language. |
| F-13 | 2026-11-12 | The product name is **Yahel**. | Decided by the owner. The interface, docs and design system in this repository now say Yahel. The backend's API title still says "WorkSync Space", so the committed API snapshot does too; design tokens keep the `--ws-` prefix, which is an internal name and not shown to anyone. | Keeping "WorkSync Space". |
| F-14 | 2026-11-12 | No AI attribution anywhere: no `Co-Authored-By` trailer and no "Generated with" line in commits or pull requests, from people or agents. | Decided by the owner. `scripts/check-attribution.mjs` fails CI if one appears. | Default tool attribution. |
| F-15 | 2026-11-12 | The backend announces API changes to this repository (event plus summary, and an issue when breaking); the design system is read by the backend from here. | Each side has one source of truth it owns and a push notice to the other, instead of copies that drift. | Copying the design system into the backend; polling a deployed backend only. |
| F-16 | 2026-11-12 | Agent reviews run on the author's machine before a pull request opens (`/pre-pr`), not in GitHub Actions. A `Review receipt` check proves all four reviewers approved the exact change. In-CI agents remain available but are off by default. | The owner has a Claude subscription, not an API key, and wants pull requests opened only for changes that already passed review. It is also cheaper and faster: problems are fixed before CI runs. | Requiring an API key in the repository. |
| F-17 | 2026-11-12 | Review is proportionate: three tiers set by the changed paths; only blockers stop a change; majors become a follow-up issue; one fix round; reviewers carry across rounds, report everything in the first, and cannot block on unchanged code in the second (security and data loss excepted). | Decided by the owner after the first end-to-end test took a small feature through four review rounds. Any of four reviewers could veto on anything above a note, and a missing test for working behaviour blocked like a defect. | Four reviewers with zero majors for every change (the original bar). The cost accepted: some imperfect changes merge with follow-up issues open. |
| F-19 | 2026-11-21 | Sign-in, account recovery and, later, account and workspace creation live in their own app, `apps/accounts`, as separate route groups with every outbound address configured. | They will be served from their own addresses, apart from the signed-in shell, and share one look and most of their code. | One app per flow (four bundles of the same code); adding the flows to the shell. The shell keeps its own sign-in page until a session can cross origins (O-1). |
| F-20 | 2026-11-21 | The Daylight look is a named token set added beside the existing tokens, with its own stylesheet (`@yahel/ui/daylight.css`). Existing tokens are unchanged. | The account designs use a different palette, display face, field size and motion from the product apps. Tokens keep every value named and contrast-checked; a separate stylesheet keeps the cost out of other apps. | Re-pointing `color.accent.*` (would restyle the shell); raw values in app CSS. |
| F-21 | 2026-11-21 | Bricolage Grotesque (variable: weight and optical size; Latin and Latin Extended) is copied into `packages/ui/assets/fonts/` with its licence (OFL 1.1), as Inter is. A scaled local fallback face holds the layout until it loads. | Rulebook 4.6 forbids third-party origins; the designs load it from Google Fonts. Copying two files adds no dependency. Source: `@fontsource-variable/bricolage-grotesque` 5.3.0. | A Google Fonts link; depending on the npm package. |
| F-22 | 2026-11-21 | Features the backend lacks are capability interfaces in `@yahel/api-client`, answered by a real endpoint, by nothing, or by a stand-in chosen in one place. Stand-ins need `VITE_STAND_INS=on`, are absent from normal builds, fail a build without `VITE_STAND_INS_ALLOW_BUILD=demo`, and show a "Demo data" label. | The designs include passkeys, an account chooser, texted codes and account help before the backend does. The interface must be buildable and testable now without pretending the server exists, and must never ship pretending. | Mocking at the network layer inside the app (hides which endpoints are missing); leaving the screens unbuilt; demo behaviour written into components. |
| F-23 | 2026-11-21 | Browser tests exercise the accounts app as a demo build served on port 4175 (`preview:demo`), not the production build. | Passkeys, the chooser and help exist only with stand-ins, and a production build may not contain them. The code under test is otherwise the same. | Switching stand-ins on at run time in a production build (defeats F-22); testing only what works without them. The cost accepted: the production bundle is proved by unit tests, the build and the budget, not by browser tests. |
| F-24 | 2026-11-21 | Flow state (email, challenge token, reset code) is held in memory only, so a reload mid-flow starts the flow again. | Rulebook 4.1: nothing sensitive in addresses or web storage. Starting again costs a few seconds; a leaked challenge or reset code costs an account. | The email in the address; session storage for flow state. |
| F-25 | 2026-11-21 | A one-time code is one text input drawn as separate boxes. | Paste, autofill from a message, Backspace and screen readers all behave correctly with one field and badly with six. It is also how the design prototype is built. | Six inputs with focus management. |
| F-26 | 2026-11-21 | When a step appears, focus goes to its first field where a keyboard is likely (hover and a fine pointer) and to its heading on touch screens. | Typing can start at once on a computer; on a phone, focusing a field would cover the question with the keyboard before it has been read. | Always the field; always the heading. |
| F-27 | 2026-11-21 | Bundle budget for the accounts app, gzip: entry 115 kB, all JavaScript 170 kB, CSS 13 kB. | A new line, sized from the measured build of slice 1 (entry 99.0, all JavaScript 145.6, CSS 11.0) with about a sixth of headroom. Slices 2 to 4 reuse the same components and load their steps as separate chunks. | No budget until all four slices exist. |
| F-28 | 2026-11-22 | The Daylight field and code-box outline is its own token, `color.daylight.control-line`, checked at 3:1 against the canvas, the field and the surface in all four themes. This departs from the drawing (22% ink, about 1.6:1). Closes O-9. | The owner's direction: control boundaries meet 3:1. It is the lightest neutral that passes. | The drawn value in the default themes with a stronger line only under increased contrast. |
| F-29 | 2026-11-22 | Every sign-in step that has an earlier step shows a Back link; the first steps show none. | The boards omit it only because each opens its step directly; the prototype shows it whenever there is history. Without it a phone user has only the browser's Back. | No Back link, as the static boards show. |
| F-30 | 2026-11-22 | The reset code is six letters and numbers ("6-character code"), and a second-step backup code is typed into an ordinary field. | The backend issues six-character alphanumeric reset codes and ten-character backup codes; the boards draw six digits for every code. | Six digit-only boxes for all three, which could not accept the real codes. |
| F-31 | 2026-11-22 | A release build of the accounts app fails unless `VITE_API_URL` and `VITE_APP_URL` are set to https addresses. `pnpm build` (used by `pnpm verify` and CI) sets `VITE_LOCAL_BUILD=local`, which allows the development fallbacks; a deployment runs `pnpm --filter @yahel/accounts build:release`. | A build with either unset used to fall back silently to `http://localhost`, sending sign-in to whatever answers there. | Removing the fallbacks (breaks development and the bundle check); a guard in the default build (CI has no deployment settings, and `.github/` is protected). |
| F-32 | 2026-11-22 | Flow requests go through `useFlowRequest`: the input is handed over by reference and dropped as it is read, outcomes are plain values, the mutation is not kept after use, and a failure is shown only during the visit in which it happened. | Passwords, codes and tokens were being kept in the TanStack mutation cache as variables and data; and resetting a pending mutation on leaving a step stranded its button. One mechanism fixes both and needs no resets or effects. | `mutation.reset()` on leave; secrets as mutation variables with a short cache time. |
| F-33 | 2026-11-22 | After a password reset succeeds it is final: the code is cleared, and if the automatic sign-in then fails the person is taken to the password step with "Your new password is saved". An expired second-step challenge likewise returns to the password step with its own message. | A failed sign-in was being reported as a failed reset, inviting a second reset with a spent code; an expired challenge read as a wrong code. | One combined failure message. |
| F-34 | 2026-11-22 | A passkey is offered whenever the browser supports WebAuthn, and the server challenge is fetched before the press so the prompt opens inside it. The `webauthn` autofill hint is not used. | Passkeys on a phone or a security key must work on devices without a built-in authenticator; some browsers only show the prompt inside the user's press. Autofill passkeys need a conditional request that is not built or testable yet. | Offering passkeys only with a built-in authenticator; keeping an autofill hint that nothing answers. |
| F-35 | 2026-11-22 | Code that two flows of the accounts app share lives in `apps/accounts/src/flow/` (the request hook, the step-field hook, step travel, the flow store, the step frame). It takes every word and all state as arguments. | Rulebook 1.3 forbids one feature importing another, and the personal flow needs what sign-in built. The hooks depend on TanStack Query and zustand, which a `type:ui` package may not. | Leaving them in `features/sign-in` and importing across features; a new package kind for one app (revisit when a second app shows a flow). |
| F-36 | 2026-11-22 | The accounts app refuses to start when a built bundle is served from anywhere but this machine (`localhost`, `127.0.0.1`, `[::1]`) without `VITE_API_URL` and `VITE_APP_URL` set to https addresses: it logs why and throws before anything is rendered or requested (`apps/accounts/src/deployment.ts`). | The build guard (F-31) can be passed with `VITE_LOCAL_BUILD=local` or as a demo, and such a bundle can still be copied to a public host, where it would offer a sign-in form that posts to a development address. | A notice page (still a page on the wrong deployment); trusting the build guard alone. |
| F-37 | 2026-11-22 | `VITE_STAND_INS_ALLOW_BUILD=demo` exempts a build from the release-address guard only when `VITE_STAND_INS=on` is also set. | The opt-in alone, left in a deployment’s settings after stand-ins were switched off, silently turned the address guard off for a real build. | Exempting on the opt-in alone. |
| F-38 | 2026-11-22 | The accounts app never shows the router’s default error screen. A step that throws is replaced, inside the flow frame, by a plain message with "Try again" and "Back to sign in" (`defaultErrorComponent`); a layout or guard that throws gets the same message with the frame; and a boundary around the router catches anything else and retries by reloading. The error itself goes to `console.error` only. | The owner met the unstyled "Something went wrong!" with a raw React message during testing. Whatever the cause, raw error text is server-internals-grade detail (rulebook 4.9) and an unstyled dead end. | Showing the message text; one boundary at the root only (would drop the frame and the flow for a single bad step). |
| F-39 | 2026-11-22 | Personal sign-up asks its questions in the designed order, but everything that needs the account to exist happens after "Agree and create account": confirming an existing email by code, confirming the recovery phone by code, and saving the passkey, the recovery email and the two choices. The boards put the emailed code at question 3 and the texted code at question 5. | The backend sends an email code only from `POST /auth/register`, and `/me/recovery/*` needs a session, so neither code can exist before the account does. Creating the account early, before the review and the agreement, was not acceptable. | Stand-in "prove this address first" endpoints; registering at question 3. The cost: the two code screens show no "03 / 06" count, the existing-email button reads "Continue" rather than "Send code", and the phone code gains "Skip for now" because the account already exists. |
| F-40 | 2026-11-22 | Progress reads "01 / 06 · Your name" above each of the six questions, and the receipt is the list on the review screen, each line with its Edit. | F-42 | 2026-11-22 | The emailed and texted codes of sign-up are six letters and numbers ("6-character code"), as in F-30. | The backend issues six-character alphanumeric codes for both; the boards draw six digits. | Digit-only boxes, which could not accept the real codes. |
| F-43 | 2026-11-22 | Creating the account is one resumable request (`requests.ts`, `create`): register, sign in, then set up, each recorded in the flow state as it completes. A repeat (a second press, "Try again", or the return from a code screen) skips what is recorded. Signing in is the only question that distinguishes "mine, already created" from "someone else’s", and it reveals nothing sign-in does not already. | Registering again and treating a duplicate as failure; an idempotency header the backend does not read. |
| F-44 | 2026-11-22 | (Corrected by F-50: no code is asked for or submitted for an address whose registration is not provably this person’s.) An existing email that already has an account is never revealed before the mailbox is proved. Nothing is asked of the server at the email step. When creation meets such an address, the person sees the same "Check your inbox" screen as anyone, a code is asked for through the neutral resend endpoint, and the screen says "If this address already has a Yahel account, sign in instead." Only someone who then enters a valid code, and whose password still does not match, is told the address has an account. A taken Yahel address says only "That address is taken." | Rulebook 4.9. The backend’s register answers `EMAIL_ALREADY_EXISTS` to anyone, which the interface cannot undo (O-12) but must not repeat. | Showing the conflict; pretending the account was created and leaving the person with no way forward. |
| F-45 | 2026-11-22 | (Corrected by F-51: the password is also dropped on every exit, and never handed back to a field.) It is never a mutation’s variables or data and never in web storage or an address. Codes are never held at all. | The account is not created until the last question, and creating it and signing in both need the password. F-32’s rule (nothing secret in the query client) still holds and is tested for this flow. | Asking for the password last (the design asks at question 4); asking for it twice. |
| F-46 | 2026-11-22 | A passkey is made on the device at question 4, as designed, before the account exists; its public half is held in memory and attached to the account after sign-in. The stand-in therefore names two endpoints: `POST /v1/auth/passkeys/registration/options` (no session, takes nothing about the person) and `POST /v1/me/passkeys/registration/verify` (session). If saving fails the account is still created and the last screen says so. A passkey is offered once per visit. | Browsers show the prompt only inside a press, and the creating screen has none. The roadmap had guessed both endpoints under `/me`, which cannot serve a challenge before there is an account. | Moving the passkey after creation (no press to hang it on, and a departure from the order drawn). | F-49 | 2026-11-22 | New settings for the accounts app: `VITE_SIGN_UP_URL` now defaults to `/personal` in this app (it was hidden while unset), `VITE_SIGN_IN_URL` defaults to `/signin`, `VITE_BUSINESS_SIGN_UP_URL` has no default (the business choice says "coming soon" until slice 3 sets it), and `VITE_MAIL_DOMAIN` defaults to `yahel.com` and must match the backend’s `PLATFORM_EMAIL_DOMAIN`. | Sign-in and sign-up will be served from different addresses later; nothing is derived from the host (F-19). | Hard-coded paths; reading the mail domain from the host. |
| F-50 | 2026-11-22 | Corrects F-44. The emailed code is submitted (`verifyEmail`), and a new one asked for, only for a registration that is provably this person’s: one this visit’s own `register` call created, or one their chosen password opens (sign-in answers `EMAIL_NOT_VERIFIED`, which the backend says only after the password matched). When register answers that the address exists and the password does not open it, the same "Check your inbox" screen is shown, but no code is requested, "Send a new code" sends nothing and answers as it would for anyone, and whatever is typed is refused locally as a wrong code. | O-11 | `RegisterDto` and the personal design do not line up. It also has no idempotency key (see F-43), accepts personal accounts only on a fixed list of public email providers the interface cannot know in advance, and its password rule differs from the design’s (O-8). **Unconfirmed registrations (see F-50, F-53):** registering an address creates an identity with the registrant’s password that stays until confirmed; registering again answers "already exists", anyone may ask for a new code for it, and a right code switches it on with the first registrant’s password. The backend must either let a new registration replace a pending one, or bind each code to the registration that issued it, and unconfirmed identities must expire. Until then the interface never confirms a registration it did not make or whose password it does not hold. **Check order:** existence is checked before the public-provider rule, so an existing address on another domain and an unknown one lead to different answers; apply the provider rule first or make the answer independent of existence.
